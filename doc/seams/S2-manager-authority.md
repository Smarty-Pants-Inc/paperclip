# S2 — Manager authority over its reporting subtree

**Status:** planned; paperclip-extend steps 1–3 draft only. **Owner:** paperclip-fork-lead. **Tracking:** [smarty-dev#20045](https://github.com/Smarty-Pants-Inc/smarty-dev/issues/20045). **Design review:** step 4 not performed; no designer/challenger approval. **Upstream:** not offered; no contact sent. Proposed destination: `doc/seams/S2-manager-authority.md` in `Smarty-Pants-Inc/paperclip`.

This is **one seam** for retirement and missing run-control authority, extending the existing S2 register row. It is not S1 Runner/Pi configuration or S3 fork release plumbing. No branch, implementation, grant, plugin installation, artifact or deployment is created by this record.

## Problem

Only the primary is static; managers must be able to task and retire their reports dynamically through the recursive **org-chart `reportsTo` tree**. An authenticated manager lacks a supported terminate primitive, arbitrary named-run cancellation, and explicit comment-interrupt authority under its own identity or the existing plugin host. Native board controls exist but are not autonomous manager authority. “Retire” means canonical termination with history retained, **not DELETE**. A stop request is not confirmed provider/process termination.

Manager authority must cover strict reports, not self, peers, ancestors, other companies or the protected static primary. Current-tree scope is distinct from task-tree scope. Existing broad configuration/reparent/assignment permissions remain independent powers and must not be misrepresented as confined by S2.

## Design

**Choice pending step 4; alternatives are mutually exclusive delivery paths, not dual authorities.** Both preserve native lifecycle/heartbeat/queued-input orchestration, grace, durable fencing, cleanup and true actor provenance. Neither introduces a runner/process supervisor, second transcript store or raw DB lifecycle writes.

| Option | Minimal core seam | Boundary / tradeoff |
| --- | --- | --- |
| **A — plugin-host additions** (fork-lead suggestion; recommended for evaluation) | Proposed `agents.terminate`, `runs.cancel`, `runs.interrupt` capabilities/client/protocol/worker-host methods, mirroring existing `agents.pause`. Extend only shared capability declaration, SDK chain, host service and small shared owning-domain orchestration plus native tests/docs. | Host enforces capability/company/native policy; trusted plugin enforces bound manager → strict-report subtree and protected primary. Company-wide capability is **not** a host subtree scope. No board token or new end-user grant UI; manager/operator settings use existing plugin/company settings. |
| **B — native scoped grants** | Proposed `agents:terminate_scope`, `runs:interrupt_scope`, and optional `agents:pause_scope` only if native agent-key REST pause is separately required. Shape `{subtreeRootAgentId:<grantee-id>}`; validate strict descendants and actual persisted target, reject null/empty/foreign-root scopes; no default grants. Small native Agent Permissions control issues fixed-root grants through existing board-only incremental route. | Server enforces each delegated agent HTTP action through native authorization including trust/user/protected-resource intersections. Larger core/UI/authority diff; cover both dedicated and PATCH status paths. Existing independent broad grants remain broad. |

**Upgrade cost / upstream fit:** A is expected to have the smaller policy/UI rebase surface, following the existing host-capability pattern and thin-core/plugin roadmap, but its SDK/protocol/host must remain version-matched and its shared native orchestration still tracks upstream changes. B adds authorization/trust/scope, route-alias, issuance/UI and stored-grant compatibility work on each rebase, in exchange for native agent-key enforcement; it is also a more direct change to deliberate board-only policy. These are qualitative source-surface estimates, not measured patch/conflict counts. Both must repeat native and independent real-path checks on each adopted release, and neither is upstream-approved.

**Common contract:** authenticated caller/company/run only, never caller-written identity; current canonical target run/agent/issue; strict descendants with cycle/depth/company/primary checks, not root-inclusive self authority. Termination targets one report and preserves history/key revocation plus canonical invalid-org-chain descendant stops; it is not recursive deletion. Managers cannot use pending-hire rejection as a substitute for board approval. Run-only stop preserves task/agent state; interrupt preserves queued successor semantics and never silently cancels a replacement run. Optional resume/invoke remain separate operations. Request-time org/grant checks are not a claim of serializable reparent/revoke locking.

**Attribution/stop compatibility:** use a real agent initiator and plugin executor where applicable, not `user` impersonation. Existing correlated native cancellation binds `{type:"board",userId}` at [`native-cancellation-request.ts:158–201`](https://github.com/paperclipai/paperclip/blob/fcf4e39b41df0b871c1391566f911b39b8af1b71/server/src/services/native-runtime/native-cancellation-request.ts#L158-L201); a new entry point needs compatible principal-bound correlation, recovery/handoff/budget intentional-stop classification and native receipts. Merely opening a route or calling `terminateAgent` is incomplete. `pausing`, durable intent, accepted HTTP and confirmed native stop are different outcomes. Preserve adapter-specific grace; no instant-stop SLA.

**Configuration:** default off; administrator installs/grants and fixes protected primary/manager eligibility. A can store the protected-primary ID in existing plugin settings. B's exact native protected-target configuration/issuance source is unresolved: no existing company `primaryAgentId` field was established. Step 4 must settle its minimal generic policy/UI/storage without inventing a Smarty-specific core flag. New grant issuance must not write unscoped rows: the pinned incremental endpoint currently writes `scope:null`; derive S2 self-root server-side if B is chosen. No generic permissions framework/editor, seeded company-wide authority, hard-delete, arbitrary root or agent self-grant. UI stays in existing plugin settings (A) or Agent Permissions / Trust (B).

## Extensions built on it

A manager-control plugin/skill uses the selected seam for **missing retirement/named-run control only**. Existing pause/resume/invoke and ordinary-comment delivery remain on upstream surfaces and do not depend on the seam. No plugin is installed or implemented here.

Day 1 (measured on 2026.1111.0-canary.4): a manager agent stops a report's live run natively by reassigning or cancelling the report's issue from inside its own run (200; run cancelled in about 3 s). A plugin tool with the existing `agents.pause`/`agents.resume`/`agents.invoke` capabilities and a subtree check covers pause/resume/wake: pause stopped a live run in under 0.5 s and settled in 7-19 s. A board-level key held by an agent is not recommended. This seam is needed only for terminate/retire-by-manager and run-only cancel/interrupt.
